# Design Spec: AI and Manual Message Tagging

**Issue:** [#267](https://github.com/forchain/UShareIPlay/issues/267)  
**Date:** 2026-08-26  
**Status:** Ready for Implementation  

## Problem Statement

In the Soul party room chat, automated messages, AI responses generated by large language models (LLMs), and manual messages sent by human operators/administrators from the backend console currently appear without source distinction. Room attendees cannot easily tell whether a given response was generated autonomously by an AI/LLM agent or sent directly by a real human administrator operating behind the scenes. This lack of transparency causes confusion, can mislead users regarding whether they are talking to an AI or a person, and reduces trust in room interactions.

## Solution

Explicitly tag outbound conversational and manual messages with standardized source markers:
- Prepend `[智能]` to all conversational replies and natural language responses generated by the LLM (Natural Language Command Resolution).
- Prepend `[人工]` to all manual text messages and operator-spoken announcements dispatched from the backend console / operator interface (e.g., plain console chat input and console-executed say commands).
- Retain existing standard system automated command responses and functional templates without false tagging, ensuring a clear and unambiguous distinction between AI-generated conversation, human-operator input, and deterministic room automation.

## User Stories

1. As a room attendee, I want AI-generated conversational responses to include a `[智能]` tag, so that I immediately know the reply was generated by an AI model and not a human.
2. As a room attendee, I want manual messages typed from the backend console to include an `[人工]` tag, so that I know the room host or human operator is personally communicating with me.
3. As a room attendee, I want `[智能]` tags on AI-generated song queries or room status answers, so that I understand the bot assistant is interpreting my question.
4. As a room attendee, I want `[智能]` tags on AI chat fallbacks when an intent is unrecognized, so that I can see the guidance comes from automated intelligence.
5. As a backend console operator, I want messages I type in the console to be automatically tagged with `[人工]`, so that I do not need to manually type `[人工]` before every message.
6. As a backend console operator, I want `:say` commands executed from the console to be automatically tagged with `[人工]`, so that my spoken announcements are transparently identified as human operator speech.
7. As a room owner, I want rule-based keywords and standard functional command confirmations (like `:play` or `:vol` status) to avoid misleading `[人工]` or `[智能]` tags, so that standard system operations remain clean and uncluttered.
8. As a room attendee, I want private replies generated by the LLM to also include the `[智能]` tag, so that I understand private guidance from the bot is AI-generated.
9. As a room attendee, I want messages that already contain the `[智能]` or `[人工]` tag to not have duplicate tags prepended, so that the message text stays neat and readable.
10. As a console operator, I want plain text entered in the console to reach the room as `[人工] <text>`, so that attendees know an admin is speaking in the room.
11. As a room attendee, I want to clearly distinguish between when a real person is answering my question versus when the AI model is answering, so that my expectations about nuance and authority are appropriately set.
12. As a developer, I want tagging to occur deterministically at the message resolution and dispatch boundaries, so that LLM omissions or prompt drift never result in untagged AI messages.
13. As a room owner, I want system timers and automated gift thank-you messages to remain distinct without improper human/AI tags, so that the origin of every room event is clear.
14. As an automated agent or spool feeder injecting messages as `Console`, I want injected manual announcements to clearly reflect operator origin with `[人工]`.

## Implementation Decisions

- **Natural Language Output Seam (LLM Tagging)**:
  In the Natural Language Command Resolution subsystem (`NaturalLanguageResolver` & `KeywordManager`), when intent translation resolves to a conversational reply (`type == 'reply'`), ensure the content is deterministically prefixed with `[智能] ` (e.g. `[智能] <text>`). If the text already starts with `[智能]` (e.g. from custom prompt or LLM generation), avoid duplicate prefixes.
- **Backend / Console Manual Output Seam (Operator Tagging)**:
  In the Chat Intake and Command Execution subsystems (`AppController` console input processing, `RuntimeQueueDrainer`, `MessageDispatch`, and `SayCommand`):
  - Plain chat text originating from the backend console (`source == 'console'` / `nickname == 'Console'`) or agent spool receives the `[人工] ` prefix before being sent to the screen or enqueued.
  - Spoken output from the `say` command initiated by the `Console` operator receives the `[人工] ` prefix.
  - If the message already starts with `[人工]`, avoid duplicate prefixes.
- **System and Functional Command Exemption**:
  Standard deterministic functional command outputs (e.g. `:play`, `:vol`, `:next`, `:timer`, gift thank-yous, room notice updates) generated by the bot engine for standard room operations remain untagged by default, preventing tag bloat on functional automation.
- **Deduplication and Idempotency**:
  Formatting helpers check for existing prefix markers (`[智能]`, `[人工]`, `【智能】`, `【人工】`) to prevent redundant double-tagging across chained handlers.

## Testing Decisions

- **Good Test Criteria**: Test external behavior and message output at the highest seams without coupling to internal parsing regexes or external LLM API sockets.
- **Modules Tested**:
  - `NaturalLanguageResolver` & `KeywordManager`: Assert that LLM-resolved replies produce messages prefixed with `[智能]`.
  - `AppController` console intake & `SayCommand` / `MessageDispatch`: Assert that plain text and `:say` commands from `Console` produce messages prefixed with `[人工]`.
  - Edge cases: Assert that messages already tagged with `[智能]` or `[人工]` do not receive duplicate tags.
- **Prior Art**:
  - `tests/test_keyword_natural_language.py`
  - `tests/test_natural_language_resolver.py`
  - `tests/test_message_dispatch.py`

## Out of Scope

- Modifying Soul UI elements or adding graphic badges inside Soul App.
- Changing third-party LLM models or prompt fine-tuning beyond standard system prompt guidance.
- Dynamic runtime configuration of custom tag strings (the tags `[智能]` and `[人工]` are fixed canonical constants).
